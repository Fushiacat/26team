# План реализации и тестирования

**Последнее обновление:** 07.09.2026

## Цель

Создать Telegram-бота, который решает задачу матчинга участников хакатона за 3 шага: анкета → список подходящих → связаться.

## Входные требования

См. `PRODUCT.md`.

**Важные ограничения:**
- Бот должен работать в Telegram
- Не использовать платные API
- Простая архитектура
- Быстрая реализация
- Матчинг должен быть релевантным (показывать подходящие анкеты)

## Архитектурные решения

### Технологии:
- **Python 3.13** — основной язык
- **aiogram 3.x** — асинхронная библиотека для Telegram ботов
- **SQLite** — простое хранилище данных (файл `data/teammatch.db`)
- **python-dotenv** — для работы с .env файлом (токен бота)

### Структура данных:

Таблица **users**:
- `id` INTEGER PRIMARY KEY AUTOINCREMENT
- `telegram_id` INTEGER UNIQUE NOT NULL
- `name` TEXT NOT NULL
- `direction` TEXT (для seeker: 09.03.01 | 09.03.03 | 09.03.04 | 27.03.04)
- `role` TEXT NOT NULL (seeker | organizer)
- `desired_role` TEXT (ba | sa | dev | devops, только для seeker)
- `about_text` TEXT (до 200 символов)
- `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Таблица **teams**:
- `id` INTEGER PRIMARY KEY AUTOINCREMENT
- `team_number` TEXT UNIQUE NOT NULL
- `created_by` INTEGER NOT NULL
- `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Таблица **team_members**:
- `id` INTEGER PRIMARY KEY AUTOINCREMENT
- `team_id` INTEGER NOT NULL
- `telegram_id` INTEGER NOT NULL
- `member_role` TEXT NOT NULL (mentor | member)
- `added_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Дополнительные таблицы не требуются — матчинг выполняется запросом к users, контакт осуществляется через `tg://user?id=<telegram_id>`.

### Логика матчинга:
- Если пользователь "Ищу команду" (seeker) → показать анкеты "Собираю команду" (organizer)
- Если пользователь "Собираю команду" (organizer) → показать анкеты "Ищу команду" (seeker)
- Из результатов исключаются пользователи, уже состоящие в команде
- Для MVP все направления и желаемые роли совместимы (нет автоматического подбора по навыкам)

### Логика команд:
- Наставник создаёт команду с уникальным номером или вступает в существующую по номеру
- Наставник может добавить свободного seeker в свою команду и удалить участника
- После добавления участник получает сообщение с составом команды и контактами
- Участник команды не отображается в доступном списке `/find`

### Что сознательно не используется:
- PostgreSQL/MySQL
- Redis (не нужен кэш)
- Сложная авторизация (достаточно telegram_id)
- Веб-интерфейс (только Telegram)
- Алгоритмы машинного обучения для матчинга
- Мини-чаты (только tg:// ссылка на профиль)

## Этапы реализации

### Этап 1: Базовая регистрация и анкета
**Наблюдаемый результат:**
- Бот запускается и отвечает на /start
- Пользователь заполняет анкету: имя, направление (одно из 4), роль (Ищу/Собираю), описание
- Данные сохраняются в SQLite
- Команда /me показывает текущую анкету
- Команда /edit позволяет обновить анкету

**Зависимости:** нет

### Этап 2: Логика матчинга
**Наблюдаемый результат:**
- Команда /find показывает список подходящих анкет
- Для роли "Ищу команду" → показывает "Собираю команду"
- Для роли "Собираю команду" → показывает "Ищу команду"
- Каждая анкета в списке имеет кнопку "Связаться"

**Зависимости:** Этап 1 (анкеты должны сохраняться)

### Этап 3: Функция "Связаться"
**Наблюдаемый результат:**
- При нажатии "Связаться" бот отправляет ссылку `tg://user?id=<telegram_id>`
- Пользователь переходит в личку с выбранным участником

**Зависимости:** Этап 2 (матчинг должен работать)

### Этап 4: Управление командами
**Наблюдаемый результат:**
- Наставник открывает `/teams`, создаёт команду или вступает в существующую
- Наставник видит состав команды, добавляет свободных участников и удаляет участников
- `/myteam` и `/me` показывают состав и ссылки на контакты
- Участники команды исключаются из результатов `/find`

**Зависимости:** Этапы 1-3

### Этап 5: Тестирование и отладка
**Наблюдаемый результат:**
- Все сценарии работают стабильно
- Обработаны краевые случаи (повторная регистрация, пустые анкеты)
- Unit-тесты проходят

**Зависимости:** Этапы 1-4

## Стратегия тестирования

**Фреймворк:** pytest

### Unit-тесты

**Что проверяется изолированно:**
- Функция сохранения анкеты (корректность данных)
- Функция фильтрации анкет (правильный матчинг по ролям)
- Фильтрация свободных участников (участники команд не попадают в выдачу)
- CRUD команд и участников команд
- Валидация направления (только 4 варианта)
- Валидация роли (только seeker/organizer)

### Интеграционные проверки

**Какие части проверяются вместе:**
- Полный цикл: регистрация → матчинг → контактная ссылка
- Полный цикл: создание команды → добавление участника → просмотр состава → удаление участника
- Работа с реальной базой данных SQLite

### Ручной сценарий

**Действие пользователя:**
1. Запустить бота, нажать /start
2. Заполнить анкету: имя "Алексей", направление "09.03.01", роль "Ищу команду", навыки "frontend, React"
3. Нажать /find — бот показывает список подходящих анкет
4. Выбрать анкету и нажать "Связаться"
5. Проверить, что открылась личка с участником
6. Наставник создаёт команду, добавляет участника и проверяет `/myteam`

**Ожидаемый результат:**
- Анкета сохранена корректно
- /find показывает релевантные анкеты (тех, кто собирает команду)
- Кнопка "Связаться" открывает личку

## Риски и откат

**Риск 1:** Мало анкет в системе — матчинг не работает
- **Снижение:** Показать пользователю сообщение "Пока нет подходящих анкет, попробуйте позже"
- **Откат:** Добавить тестовые анкеты для демонстрации

**Риск 2:** Telegram API недоступен или rate limiting
- **Снижение:** Использовать асинхронные запросы, добавить обработку ошибок
- **Откат:** Локальное тестирование без реального бота

**Риск 3:** Потеря данных при перезапуске
- **Снижение:** Использовать SQLite с commit после каждой операции
- **Откат:** Резервное копирование базы данных
